# Правила командной разработки

В этом документе описаны общие правила работы над проектом **BioFormat Toolkit**.

Цель правил — обеспечить согласованную разработку, упростить объединение модулей и избежать конфликтов при совместной работе с репозиторием.

## 1. Общие положения

- Каждый участник отвечает за реализацию своей части проекта.
- Разработка ведётся в общем GitHub-репозитории.
- Каждый участник работает в отдельной ветке.
- Ветка `main` содержит общую, проверенную версию проекта.
- Изменения, затрагивающие архитектуру или интерфейсы общих классов, предварительно обсуждаются с командой.
- О возможных задержках выполнения задач необходимо сообщать заранее.

## 2. Работа с ветками

Названия веток пишутся на английском языке и должны отражать их назначение.

Примеры:

- `feature/vcf`
- `feature/fastq`
- `feature/sam`
- `feature/fasta`
- `docs/sphinx`
- `fix/vcf-header`

Новые рабочие ветки создаются от актуальной версии `main`.

Не следует отправлять изменения непосредственно в `main`. Для объединения готового кода используется Pull Request.

Название рабочей ветки участник выбирает самостоятельно. После первого коммита ветку необходимо отправить в удалённый репозиторий, чтобы она была доступна остальным участникам команды.

## 3. Сообщения коммитов

Сообщения коммитов пишутся на русском языке.

Основные рекомендации:

- Кратко и понятно описывать внесённые изменения.
- Использовать глаголы в неопределённой форме: «Добавить», «Реализовать», «Исправить», «Обновить».
- По возможности объединять в одном коммите только логически связанные изменения.
- Не использовать неинформативные сообщения, например «правки», «готово», «изменения».

Примеры корректных сообщений:

- `Добавить базовый класс Reader`
- `Реализовать чтение VCF-файлов`
- `Исправить обработку пустого FASTA-файла`
- `Добавить тесты для SamReader`
- `Обновить документацию проекта`

## 4. Pull Requests и проверка кода

После завершения задачи участник отправляет изменения в свою ветку на GitHub и создаёт Pull Request в `main`.

В описании Pull Request необходимо кратко указать:

- какие изменения были внесены;
- какая функциональность реализована;
- как проверялась работоспособность кода;
- есть ли известные ограничения или нерешённые проблемы.

Перед объединением изменения проходят Code Review.

Если при проверке обнаружены ошибки или возникают вопросы, замечания оставляются непосредственно в Pull Request, по возможности с привязкой к соответствующим строкам кода.

После внесения исправлений участник отправляет новые коммиты в ту же ветку. Создавать новый Pull Request для этих исправлений не требуется.

Объединение изменений с `main` выполняется после успешной проверки.

## 5. Стиль написания кода

- Названия файлов, классов, методов и переменных пишутся на английском языке.
- Следует придерживаться рекомендаций PEP 8.
- Для методов и функций рекомендуется использовать аннотации типов.
- Классы и публичные методы должны сопровождаться docstrings.
- Не следует дублировать функциональность, уже реализованную в общих классах.
- Перед изменением согласованных интерфейсов необходимо обсудить это с командой.

### Работа с путями к файлам

Для формирования путей рекомендуется использовать стандартный модуль `pathlib`.

Не следует прописывать в общем коде абсолютные пути, зависящие от компьютера конкретного участника.

Программа должна корректно работать на разных операционных системах, в том числе Linux, macOS и Windows.

## 6. Работа с входными данными

Большие входные файлы и личные рабочие данные не добавляются в репозиторий.

Для локальных данных используется папка `data/` в корне проекта, исключённая через `.gitignore`.

Небольшие тестовые файлы, необходимые для проверки программы, размещаются в `tests/data/` и хранятся в общем репозитории.

Это позволяет всем участникам запускать тесты на одинаковых входных данных.

## 7. Тестирование

Каждый участник самостоятельно проверяет реализованную им функциональность.

При тестировании необходимо учитывать не только корректные входные данные, но и возможные ошибочные ситуации.

Автоматические тесты размещаются в папке `tests/`.

Рекомендуется разделять их по форматам:

- `test_fasta.py`
- `test_fastq.py`
- `test_sam.py`
- `test_vcf.py`

Общие результаты тестирования фиксируются в документе `TESTING.md`.

Перед объединением изменений необходимо убедиться, что новая функциональность работает и не нарушает уже реализованные части проекта.

## 8. Документация

Каждый участник отвечает за документирование собственного кода.

Общая документация проекта формируется на основе подготовленных docstrings с использованием Sphinx.

Назначение основных документов:

- `README.md` — описание проекта, зависимости, установка и запуск.
- `ARCHITECTURE.md` — структура проекта, иерархия классов и согласованные интерфейсы.
- `CONTRIBUTING.md` — правила командной разработки.
- `TESTING.md` — описание проведённого тестирования.

При изменении функциональности необходимо при необходимости обновлять соответствующую документацию.

## 9. Коммуникация

Для организации работы используются следующие инструменты:

- **Telegram** — оперативные вопросы, организационные обсуждения и практические инструкции по Git.
- **GitHub Issues** — постановка задач и отслеживание их выполнения.
- **GitHub Projects** — отслеживание общего прогресса команды.
- **Pull Requests** — обсуждение изменений в коде и Code Review.

Решения, влияющие на архитектуру проекта, после обсуждения фиксируются в `ARCHITECTURE.md`.

Если при выполнении задачи возникают трудности, рекомендуется своевременно сообщить об этом команде, чтобы не задерживать последующие этапы разработки.

---

Данные правила могут дополняться и изменяться по согласованию участников команды.
